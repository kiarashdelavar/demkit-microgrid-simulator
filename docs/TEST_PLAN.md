# Test Plan — Current Simulation and Future Releases

**Status:** Proposed checks — do not mark them passed until a test has been executed and evidence recorded.

## Test approach

Use a repeatable Windows baseline first. Record the operating system, Python/Node versions, Git commit, steps, expected output, actual output, screenshot/log location, and pass/fail result. Then repeat relevant cases on clean and cross-platform environments after a launcher or package exists.

## Functional smoke tests

| ID | Scenario | Expected behaviour |
| --- | --- | --- |
| T-01 | Start backend and Node web server | Browser loads at `localhost:3002`; DEMKit responds on `3001` |
| T-02 | Start Mission, pause and resume | Simulated time moves only while running |
| T-03 | Add and remove supported devices | UI and DEMKit state remain consistent |
| T-04 | Move an EV between houses | EV is removed/created as intended; no ghost devices |
| T-05 | Test device slots and coin spending | Valid purchases reduce balance; invalid actions are rejected |
| T-06 | Complete a learning goal | Reward granted once and displayed clearly |
| T-07 | Use Solar, Smart and manual battery modes | Charge/discharge respects capacity and power bounds |
| T-08 | Add multiple batteries to a house | Energy/state values remain valid; exceptions are recorded |
| T-09 | Create an overload and restore a burned cable | Warning appears and recovery behaves as designed |
| T-10 | Refresh or reconnect the browser | Display reconnects and shows current simulation state |
| T-11 | Stop DEMKit while Node remains running | Error is understandable; app does not silently report success |
| T-12 | Resize devices using supported controls | Simulation parameters match shown device settings |

## Installation, reliability and packaging tests

| ID | Scenario | Expected behaviour |
| --- | --- | --- |
| I-01 | New checkout on clean Windows environment | Documented setup completes without hidden manual fixes |
| I-02 | Project directory contains spaces | Paths resolve and services start |
| I-03 | Port 3001 or 3002 is already occupied | Launcher reports conflict and avoids false success |
| I-04 | Python/Node component missing or fails | User receives a clear diagnostic and next step |
| I-05 | Start and stop application repeatedly | Processes shut down cleanly and ports are reusable |
| I-06 | No InfluxDB service | Interactive simulation still works if logging is designed to be optional |
| I-07 | No network after installation | App starts from local assets when feasible; failures are documented |
| I-08 | Windows packaged release | Fresh user launches without installing developer tooling manually |
| I-09 | macOS build | Tested install/launch on actual targeted architecture, if supported |
| I-10 | Linux build | Tested install/launch on targeted distribution, if supported |
| I-11 | Classroom usability | Teacher can start and reset an exercise using guidance |

## Minimum proposed release gate

- Essential smoke tests pass or have documented limitations accepted by project supervisors.
- Launcher and package tests pass on each OS claimed as supported.
- Installation instructions match the release, including prerequisites and troubleshooting.
- No real secrets or local runtime environments are included in committed files or release artifacts.
- At least one short teacher/student usability walkthrough has been recorded.

Cross-platform testing requires real evidence. A package generated by CI is **not**, by itself, proof that the program works on that platform.
